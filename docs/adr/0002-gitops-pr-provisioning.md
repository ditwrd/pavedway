# Provisioning and teardown flow through GitOps PRs, not direct cluster writes

Pavedway's self-service provisioning ([ProvisioningTemplate flow](https://github.com/ditwrd/pavedway/issues/10)) could either call the Kubernetes/Crossplane API directly to create and delete XRs, or render the manifest and open a PR/MR against the GitOps repository an existing Argo CD instance already reconciles from. Since pavedway is designed to run alongside an org's existing Argo-based GitOps workflow, a direct-API write path would make pavedway a second independent writer of cluster state alongside Argo — risking silent overwrites and defeating the audit trail (who approved what, when) GitOps already provides. We considered pavedway owning its own apply/reconcile loop to keep the self-service UX synchronous, but that duplicates reconciliation Argo already does reliably and fights the deployment model self-hosters running Argo already have.

We decided: the built-in Crossplane Provisioning-action plugin renders the XR manifest — carrying pavedway correlation annotations so a later discovery sync can match the resulting cluster object back to the request that created it — and opens a PR/MR against the org's configured GitOps repo. Argo CD is the sole applier: it merges the PR, applies the XR, and later prunes it on removal. A `ProvisioningTemplate`'s configured approval (bool + approver list) maps onto the PR/MR's required reviewers, not a separate in-app approval step. Pavedway never issues a Kubernetes API write for provisioning or teardown.

Consequence: provisioning is asynchronous. A Component appears in the catalog immediately in a pending state on request, but the underlying XR entity only appears once the PR merges and the next discovery sync ([issue #9](https://github.com/ditwrd/pavedway/issues/9)) picks up the real object; drift is whatever Crossplane's and Argo's own status/conditions already report, not a pavedway-built engine.

This is hard to reverse (rearchitecting to synchronous direct-apply later changes the whole request lifecycle and catalog entity state machine), surprising without this context (most self-service IDP flows apply directly — "why does clicking Provision only open a PR" needs an explanation), and a real trade-off (loses synchronous instant provisioning in exchange for GitOps auditability and avoiding a split-brain writer against the org's existing Argo workflow).
