# Two-tier Org/Team RBAC backed by apache-casbin, with permission sets as inheritable roles

[Design Auth/SSO provider architecture and RBAC permission model](https://github.com/ditwrd/pavedway/issues/13) originally locked a fixed Admin/Editor/Viewer role set, org-wide only (no per-team scoping), no custom role authoring, with policy evaluation as fixed logic built into core. [Rework organization/team/user RBAC hierarchy with Casbin](https://github.com/ditwrd/pavedway/issues/19) revisited this: teams need their own resource-scoped roles distinct from org-wide platform-administration roles, and admins need to compose custom roles from shared, reusable permission bundles instead of hand-authoring a new role for every seniority tier — the fixed 3-role model doesn't scale to that.

We decided: adopt [apache-casbin](https://casbin.org/) as the policy engine, using its built-in **RBAC with domains** model with `domain = Team` — org-wide roles (mainly platform administration: super admin, user admin) and team-scoped roles (mainly resource management within that team) are both first-class, and a Team role takes precedence over an Org role on that team's own resources (most-specific-wins). A **permission set** is not a new data model — it's simply a Casbin role with no direct member assignments, that other roles inherit from via Casbin's native role-inheritance graph (`g`), letting an org admin define reusable bundles (e.g. "view-own-team", "view-partner-team-subset") once and compose them into as many custom roles as needed, at both Org and Team scope. Custom roles are now in scope for v0.1, superseding #13's "no custom role authoring." Policy rows are stored via Casbin's official SQL adapter (e.g. gorm-adapter), not a hand-rolled adapter. The existing `ownedBy`-grants-edit override stays a separate fast-path check evaluated before Casbin, not modeled as per-resource Casbin policy rows — it stays a relation lookup, not a policy-table entry per owned resource.

This is hard to reverse (once teams have real custom roles and permission-set graphs seeded into Casbin's policy tables, swapping engines means migrating every tenant's role graph, not just application code), surprising without context (#13 explicitly said policy evaluation is "fixed logic... not a plugin interface" and rejected custom roles — the resolution here is that policy evaluation is still core, not a plugin, just backed by a purpose-built third-party engine instead of hand-rolled conditionals, and the custom-role scope decision is an explicit, later revision, not an oversight), and a real trade-off (hand-rolled permission checks are simpler to read for a small fixed role set, but don't compose; Casbin's role-inheritance graph solves permission-set sharing for free at the cost of a new dependency and an "everything is a role" mental model that a contributor expecting a dedicated `PermissionSet` table won't guess at without this note).
