# Open-core boundary: tenant isolation ships in OSS core, SaaS ops tooling stays closed-source

Pavedway's OSS core is never feature-paywalled — the paid tier is hosting plus an SLA/support contract, not gated product capability. This forced a specific question: multi-tenancy is inherently a SaaS-operator concern, so where does *its* code live? We considered shipping the whole multi-tenant stack (isolation primitives *and* the tenant-provisioning/billing/usage-metering tooling that operates it) as one closed-source SaaS layer outside the repo, which would have been simpler to build but leaves the isolation guarantees unauditable by self-hosters who might want to run multi-tenant themselves. We instead draw the line at the primitive: tenant-scoped storage and auth isolation ship in OSS core, auditable and usable by any self-hoster, while the operational tooling that only makes sense for running pavedway's own SaaS (tenant provisioning console, billing hooks, usage metering) lives in a separate closed-source operator/service that calls pavedway's OSS APIs from the outside. This keeps the trust-critical isolation logic open while still letting the hosted-only operational surface stay proprietary, and it's why that operator code won't appear in this repo even though the project is Apache-2.0.

v0.1 itself is single-tenant only — this boundary governs where future multi-tenancy code will live, not something v0.1 builds; the multi-tenancy/organization model itself remains fog until auth/permissions work ripens it.
