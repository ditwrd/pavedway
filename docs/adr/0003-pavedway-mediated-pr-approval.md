# Approval and merge happen inside pavedway, not via native Git-provider reviews

[Design Crossplane provisioning governance](https://github.com/ditwrd/pavedway/issues/15) originally mapped a `ProvisioningTemplate`'s approver list onto the PR/MR's required reviewers — approval happened natively on the Git provider, pavedway stayed out of the way. [Design pavedway-mediated Git-provider PR approval and identity-linking flow](https://github.com/ditwrd/pavedway/issues/18) revisited this: since a provisioning request can span multiple repositories (assumed common), an approver checking each repo's own PR queue doesn't scale — they need one unified queue inside pavedway. But GitHub review attribution should still show the real human, and branch-protection "required reviews" rules should still see a genuine review, not a bot comment.

We decided: every pavedway User links their own Git-provider account via a dedicated OAuth "Connect your GitHub account" flow, independent of the login SSO session ([issue #13](https://github.com/ditwrd/pavedway/issues/13)'s OIDC provider need not be GitHub). A request's PR is opened using the *requester's* own linked Git identity as the author. Approval, rejection ("Request changes" + comment), and diff review all happen inside pavedway's UI; on each action pavedway calls a new **Git-provider plugin interface** (a 5th interface alongside EntityProvider/Processor/Provisioning-action/Auth-SSO-provider from [issue #3](https://github.com/ditwrd/pavedway/issues/3)) that submits the real review, as the acting approver's own linked identity, against the Git provider's API. Once the approver quorum for the template is met (default: any one of the listed approvers; configurable to a custom N) and the repo's required status checks pass, pavedway auto-merges the PR via the same plugin — closing the loop without the user needing to leave pavedway. Any pavedway action requiring a Git-provider call is blocked with an inline "connect your account first" prompt if the acting user hasn't linked an identity yet; nothing is recorded as approved/rejected in pavedway without the matching real Git-provider action succeeding.

This does not change [ADR 0002](0002-gitops-pr-provisioning.md)'s core boundary: Argo CD remains the sole applier of cluster state, and pavedway still never issues a Kubernetes API write for provisioning. What changes is who submits the *Git-provider* review/merge action — pavedway, using per-user linked credentials, instead of the Git provider's own review UI.

This is hard to reverse (per-user OAuth token storage and a new plugin interface are real infrastructure to unwind), surprising without context (a "GitOps PR" system where pavedway still holds write-capable per-user Git credentials and auto-merges looks, at a glance, like it reintroduces the direct-writer risk ADR 0002 avoided — the distinction is *cluster* writes vs. *Git-provider* actions), and a real trade-off (native per-repo GitHub review UX vs. one unified cross-repo approval surface, at the cost of storing and refreshing per-user OAuth tokens).
