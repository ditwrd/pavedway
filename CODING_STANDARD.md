# CODING_STANDARD.md

> Clear is better than clever.

Human-judgment Go style rules for pavedway. Formatting, naming, and
mechanical rules are enforced automatically by `.golangci.yml` (gofumpt,
goimports, gocritic, revive, wsl_v5, godot, misspell, and ~40 more linters);
this document covers the rules that require judgment. Where the two overlap,
the linter wins. When a rule here is deliberately ignored, add a code
comment naming the deviation (e.g. `// ponytail: single-org lookup, replace
with tenant-scoped lookup when multi-tenancy lands`).

Source of truth: the `golang-code-style` skill
(`/home/dit/.agents/skills/golang-code-style`). This file is the repo-local
distillation; the skill is the authority.

## Enforcement

- Run `golangci-lint run ./...` from the repo root. The gate is
  `issues.new-from-rev: HEAD` (`.golangci.yml`): only code changed since
  `HEAD` is reported. New code must be lint-clean — zero issues.
- Generated code (`internal/store/*.sql.go`, marked
  `// Code generated by sqlc. DO NOT EDIT.`) is exempt from hand-written
  style rules. Never edit generated files; regenerate instead.
- Test files are included in linting (`tests: true`) and follow the same
  rules, with one relaxation: test helpers may take more parameters when an
  options struct would obscure the test (see "Function Design").
- Pre-commit verification: `go build ./... && go vet ./... && golangci-lint
  run ./... && go test ./...`.

## Line Length & Breaking

No rigid line limit, but lines beyond ~120 characters MUST be broken at
semantic boundaries — not arbitrary column counts. Function calls with 4+
arguments MUST use one argument per line, even when the code was written
single-line:

```go
handleUsers(
    w,
    r,
    serviceName,
    cfg,
    logger,
)
```

When a function signature is too long, the real fix is usually fewer
parameters (an options struct), not better wrapping.

## Variable Declarations

- `:=` for non-zero values; `var` for zero-value initialization. `var`
  signals "this starts at zero":

```go
var count int              // zero value, set later
name := "default"          // non-zero
```

- Slices and maps MUST be initialized explicitly, never nil. Nil maps panic
  on write; nil slices serialize to `null` in JSON, surprising API clients:

```go
users := []User{}          // always initialized
m := map[string]int{}      // always initialized
users := make([]User, 0, len(ids))  // preallocate when capacity is known
```

- Preallocate only when capacity is known — `make([]T, 0, 1000)` for a
  common case of 10 items wastes memory.
- Composite literals MUST use field names — positional fields break when a
  type adds or reorders fields:

```go
srv := &http.Server{
    Addr:        ":8080",
    ReadTimeout: 5 * time.Second,
}
```

## Control Flow

### Reduce Nesting

Errors and edge cases MUST be handled first with early returns; keep the
happy path at minimal indentation:

```go
func process(data []byte) (*Result, error) {
    if len(data) == 0 {
        return nil, errors.New("empty data")
    }
    parsed, err := parse(data)
    if err != nil {
        return nil, fmt.Errorf("parsing: %w", err)
    }
    return transform(parsed), nil
}
```

### Eliminate Unnecessary `else`

When an `if` body ends in `return`/`break`/`continue`, the `else` MUST be
dropped. For simple assignments, default-then-override:

```go
// Good — default, then override
level := slog.LevelInfo
switch {
case debug:
    level = slog.LevelDebug
case verbose:
    level = slog.LevelWarn
}
```

### Complex Conditions

`if` conditions with 3+ operands MUST be extracted into named booleans — a
wall of `||` hides business logic:

```go
isAdmin := user.Role == RoleAdmin
isOwner := resource.OwnerID == user.ID
if isAdmin || isOwner {
    allow()
}
```

Keep expensive checks inline in the condition for short-circuit benefit.

### Init Scope and Switch

- Scope variables to the `if` when only needed for the check:
  `if err := validate(input); err != nil { return err }`.
- Comparing the same variable 3+ times via if-else SHOULD be a `switch`.

## Function Design

- Short and focused: one function, one job.
- SHOULD have ≤4 parameters. Beyond that, use an options struct.
- Parameter order: `context.Context` first, then inputs, then output
  destinations.
- Prefer `range` over index-based loops; `range n` (Go 1.22+) for simple
  counting.
- Naked returns only in very short functions (1-3 lines) where return
  values are obvious.

```go
func FetchUser(ctx context.Context, id string) (*User, error)
func SendEmail(ctx context.Context, msg EmailMessage) error  // grouped into struct
```

## Value vs Pointer Arguments

Pass small types (`string`, `int`, `bool`, `time.Time`) by value. Use
pointers when mutating, for large structs (~128+ bytes), or when nil is
meaningful.

## Code Organization

- **Group related declarations**: type, constructor, methods together.
- **Order within a file**: package doc, imports, constants, types,
  constructors, methods, helpers.
- **One primary type per file** when it has significant methods.
- **Package docs**: every non-main package has a `// Package <name> ...`
  comment (revive `package-comments` enforces).
- **Blank imports** (`_ "pkg"`) register side effects — restrict to `main`
  and test packages.
- **Dot imports** pollute the namespace — never use in library code.
- **Unexport aggressively** — every exported name is a commitment;
  unexporting later is a breaking change. Use `gopls` rename to do it
  safely across call sites.

## String Handling

- `strconv` for simple conversions (`strconv.Itoa`, `strconv.Quote`);
  `fmt.Sprintf` for complex formatting. (`perfsprint` enforces.)
- Use `%q` in error messages to make string boundaries visible.
- `strings.Builder` for concatenation in loops; `+` for simple
  concatenation.
- Errors MUST be wrapped with `%w` when adding context
  (`fmt.Errorf("loading refresh token: %w", err)`) so `errors.Is/As` keep
  working. (`errorlint` enforces.)

## Type Conversions & Philosophy

- Prefer explicit, narrow conversions. Use generics over `any` when a
  concrete type will do.
- Use `slices` and `maps` standard packages; for filter/group-by/chunk, use
  `github.com/samber/lo`.
- Avoid `reflect` unless necessary.
- Don't abstract prematurely — extract when the pattern is stable.
- Minimize public surface.
- "A little copying is better than a little dependency."

## Logging

- Diagnostics go through `log/slog` (`slog.Error`, `slog.Info`, ...) with
  key-value pairs — NEVER `log.Printf`/`fmt.Print*` to stdout, which
  corrupts piped program output (`sloglint`/`loggercheck` enforce key-value
  shape).

## Deviations

Every deliberate deviation carries a `ponytail:` comment naming the
shortcut, its ceiling, and the upgrade path. `// ponytail:` is the repo
marker for "intentional simplification" — see `ponytail-debt` for the
ledger.
